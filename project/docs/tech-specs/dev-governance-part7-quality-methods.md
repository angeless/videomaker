# 第七部分：质量工程方法论（§7.1–§7.7）

> **导航**: [← 返回索引](dev-governance.md) | [← 第六部分：版本交叉审计](dev-governance-part6-audit.md)
>
> 本文件定义开发过程中的质量工程方法论，包括 TDD、系统化调试、代码审查、工作区隔离、并行开发和完成前验证。
> 这些方法论嵌入到现有的 Phase 1-8 流程中，作为各阶段的执行标准。
>
> **TL;DR（上下文受限时仅读此块）**:
> 六条铁律：① Phase 2 必须 TDD（先写失败测试再写代码）；② 门禁失败必须系统化调试（4 阶段根因调查，最多 3 次修复尝试）；③ Phase 4 审计后派发独立子 Agent 做代码审查；④ 大版本开发用 Git Worktree 隔离；⑤ 独立任务可并行派发子 Agent；⑥ 任何完成声明必须附带新鲜的验证证据。

---

## §7.1 TDD — 测试驱动开发（嵌入 Phase 2）

### 铁律

```
禁止在没有失败测试的情况下编写生产代码
```

### 适用范围

- Phase 2 的所有编码工作（新功能、Bug 修复、重构）
- 例外：纯配置文件修改、migration 脚本、静态资源（无需 TDD）

### Red-Green-Refactor 循环

| 步骤 | 动作 | 验证 | 禁止 |
|------|------|------|------|
| **RED** | 写一个最小测试，描述期望行为 | 运行测试，**必须看到失败** | 跳过运行直接写代码 |
| **GREEN** | 写最简单的代码让测试通过 | 运行测试，**必须看到通过** | 写超出测试要求的代码 |
| **REFACTOR** | 清理代码（仅在 GREEN 之后） | 运行全部测试，**必须全部通过** | 在 RED/GREEN 阶段重构 |

### 检查清单（每个测试循环必须满足）

- [ ] 测试先于代码存在
- [ ] 亲眼看到测试失败（不是假设它会失败）
- [ ] 失败原因正确（测试的是目标行为，不是语法错误）
- [ ] 通过的代码是最简实现
- [ ] 每个测试只测一个行为（名字里有 "和" 就拆分）

### 异常处理

| 情况 | 处理 |
|------|------|
| 测试立刻通过（没有失败） | 测试的是已有行为，重写测试 |
| 测试报错（不是断言失败） | 修复测试本身的错误，重新运行 |
| 不确定如何测试 | 先写最外层的集成测试，再逐步细化 |
| 项目没有测试框架 | Phase 2 第一步：搭建测试框架（参考 testing-strategy.md） |

## §7.2 系统化调试（嵌入门禁失败修复流程）

### 铁律

```
禁止在未完成根因调查的情况下提出修复方案
```

### 适用范围

- Phase 2/3/4 门禁失败后的修复流程
- 替代原 §0.12 中的简单"自动修复并重跑"

### 四阶段调查流程

**Phase D1：根因调查**（必须完成才能进入 D2）

1. 完整阅读错误信息（全部 stack trace、行号、上下文）
2. 稳定复现（记录精确步骤，确保每次都能触发）
3. 检查最近改动：`git diff HEAD~3` 或 `git log --oneline -5`
4. 在多组件系统中，在每个边界添加诊断日志
5. 反向追踪数据流：从错误点往回追，找到第一个偏离预期的位置

**Phase D2：模式分析**（必须完成才能进入 D3）

1. 找到代码库中类似的正常工作的代码
2. 完整阅读参考实现（不是部分适配）
3. 逐条列出差异（无论多小）
4. 理解依赖关系（组件、配置、假设）

**Phase D3：假设与验证**（必须完成才能进入 D4）

1. 形成单一假设："我认为 X 是根因，因为 Y"
2. 最小化测试（只改一个变量）
3. 验证假设是否成立
   - 成立 → 进入 D4
   - 不成立 → 回到 D1 形成新假设

**Phase D4：实现修复**

1. **先写失败测试**（与 §7.1 TDD 联动）
2. 实现单一修复（只改一处，只修根因）
3. 验证修复（目标测试通过，其他测试不破）
4. 修复无效 → 计数修复尝试次数

### 修复尝试上限

| 尝试次数 | 动作 |
|---------|------|
| ≤ 2 次 | 回到 D1 重新调查 |
| = 3 次 | **停止**，质疑架构设计（可能不是 Bug 而是设计问题） |
| > 3 次 | 升级为人工介入（§0.4 停止条件） |

### 停止信号（出现以下想法时立刻停止）

- "先临时修一下，以后再查原因"
- "改一下 X 看看行不行"
- "跳过测试，手动验证"
- "再试一次修复"（已经试过 2 次以上）
- 每次修复都暴露出不同位置的新问题

## §7.3 代码审查流程（嵌入 Phase 4 之后）

### 铁律

```
关键任务在合并前必须经过独立代码审查
```

### 适用范围

- 每个任务的 Phase 4 审计通过后
- 合并到 main 之前（必须）
- 功能项边界（建议）

### 请求审查流程

1. 获取变更范围：
   ```bash
   BASE_SHA=$(git merge-base HEAD main)
   HEAD_SHA=$(git rev-parse HEAD)
   ```
2. 使用 Agent 工具派发 code-reviewer 子 Agent
3. 提供：实现了什么、计划/需求、变更范围、关键决策
4. 根据反馈分级处理：

| 级别 | 处理 |
|------|------|
| Critical | 立刻修复，阻断合并 |
| Important | 修复后再继续 |
| Minor | 记录，后续处理 |
| 不同意 | 用技术理由反驳（不是社交客气） |

### 审查结果归档（强制）

Code Review 结果**必须**保存到文件，不允许在对话中消失：

- **任务级 Review**：保存到 `docs/versions/code-review-v{X.Y.Z}.md`
- **内容**：审查范围（SHA）、发现列表（分级）、处理结果（已修复/已记录/已反驳）
- **时机**：在 Phase 6 commit 之前保存
- **Phase 6 门禁追加**：`code-review-v{X.Y.Z}.md` 文件必须存在

### 接收审查规则

**必须做的**：
1. 完整阅读反馈，不带情绪
2. 用自己的话复述要求（或提问确认）
3. 对照代码库验证建议是否正确
4. 逐条实现，每条单独测试
5. 验证无回归

**禁止做的**：
- "你说得太对了！"（情绪化同意）
- "好建议！"（空洞赞美）
- "让我立刻实现"（未验证就动手）
- 盲目实现所有建议（有些可能不适用）

**何时反驳**：
- 建议会破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（过度设计）
- 在当前技术栈中技术上不正确

## §7.4 Git Worktree 隔离（嵌入 /mode-autocode）

### 适用范围

- 大版本开发（推荐）
- 需要与当前工作区隔离的功能开发
- 并行开发多个独立功能时

### 创建流程

1. 检查项目现有 worktree 目录：`.worktrees/`（优先）或 `worktrees/`
2. 确保 worktree 目录在 `.gitignore` 中
3. 创建 worktree：
   ```bash
   git worktree add .worktrees/<feature-name> -b <branch-name>
   ```
4. 在 worktree 中运行项目初始化（`npm install` / `pip install` 等）
5. 运行基线测试确认环境正常
6. 在 worktree 中开发，完成后合并回主分支

### 安全验证（创建前必须）

- worktree 目录必须在 `.gitignore` 中（不在就加上并 commit）
- 基线测试必须通过（不通过则报告并询问是否继续）

## §7.5 并行子 Agent 派发（嵌入 Phase 2）

### 适用范围

- 3 个以上独立的测试文件/子系统需要修复
- 多个独立任务可以同时进行（无共享状态）
- 每个问题可以独立理解，不需要其他问题的上下文

### 不适用

- 失败之间有关联（修一个可能修好其他的）
- 需要理解全局状态
- Agent 之间会互相干扰（修改同一个文件）

### 派发流程

1. **识别独立领域**：按故障类型分组，确认无交叉依赖
2. **创建聚焦任务**：每个 Agent 只处理一个领域，明确范围和约束
3. **并行派发**：使用 Agent 工具同时派发多个子 Agent
4. **审查与整合**：
   - 检查每个 Agent 的返回结果
   - 确认无冲突（是否修改了同一文件？）
   - 运行全量测试
   - 抽查验证

### Agent Prompt 要求

- **聚焦**：只处理一个明确的问题领域
- **自包含**：包含理解问题所需的全部上下文
- **明确输出**：说清楚 Agent 应该返回什么
- **有约束**：说清楚不要改什么

## §7.6 完成前验证（嵌入 Phase 6 门禁）

### 铁律

```
禁止在没有新鲜验证证据的情况下声称任务完成
```

### 验证流程（每一步都不能跳过）

1. **识别**：什么命令可以证明这个声明？
2. **执行**：运行完整命令（新鲜的、完整的）
3. **阅读**：完整输出、检查 exit code、计数失败数
4. **确认**：输出是否支持声明？
   - 否 → 说明实际状态 + 证据
   - 是 → 声明 + 证据
5. **此时才可以**做出声明

### 证据要求

| 声明 | 必须包含 | 不够格 |
|------|---------|--------|
| 测试通过 | 测试命令输出：0 failures | 之前的运行结果、"应该通过" |
| 构建成功 | 构建命令：exit 0 | lint 通过、日志看着正常 |
| Bug 已修复 | 复现原始症状：通过 | 改了代码、假设修好了 |
| 需求满足 | 逐条检查清单 | 只靠测试通过 |
| 子 Agent 完成 | VCS diff 显示变更 | Agent 报告"成功" |

### 停止信号（出现以下想法时立刻停止）

- 使用"应该"、"可能"、"似乎"
- 在验证之前表达满意（"完美！"、"搞定！"）
- 准备 commit/push/PR 但没有验证
- 信任子 Agent 的成功报告而不独立验证
- 依赖部分验证
- 想着"就这一次"跳过

## §7.7 报告强制归档与编辑历史（嵌入 Phase 6 + Phase 8）

### 铁律

```
1. 所有任务报告和版本报告必须持久化到文件，不允许仅存在于对话中
2. 所有文件修改必须使用 Edit（增量编辑），禁止使用 Write（全量覆盖）
3. 修复导致的报告更新必须保留编辑历史，不允许删除原始记录
```

### 编辑 vs 覆盖（全局原则）

**此规则适用于所有文件操作，不仅限于报告。**

| 操作 | 正确做法（Edit） | 错误做法（Write/覆盖） |
|------|-----------------|---------------------|
| 更新报告 | 在原文件末尾追加修订记录 | 删除原文件，重新生成 |
| 修改开发计划 | 编辑具体字段（状态、日期、备注） | 用新计划覆盖整个文件 |
| 升级规范文件 | 插入新章节、更新已有段落 | 用模板覆盖项目定制内容 |
| 更新 CHANGELOG | 在 [Unreleased] 下追加条目 | 重写整个 CHANGELOG |
| 更新 TODO_NEXT.md | 编辑"下一步"字段 | 重写整个文件 |
| Code Review 修复 | 追加修订记录到 review 报告 | 删除原始发现重写 |

**为什么禁止覆盖**：
- 覆盖 = 丢失项目特有的定制内容（规范文件中用户加的自定义规则）
- 覆盖 = 丢失历史记录（报告中之前发现的问题）
- 覆盖 = 无法追溯变更原因（git diff 看到的是全文替换，不是增量变更）
- Edit 工具只发送 diff，Write 工具发送全文——Edit 更精准、更安全、更易审查

### 强制归档清单

| 报告类型 | 路径 | 产出时机 | 门禁检查 |
|---------|------|---------|---------|
| 任务报告 | `docs/versions/task-report-v{X.Y.Z}.md` | Phase 6 收尾 | Phase 6 ③ C 步骤：文件必须存在且内容完整 |
| Code Review 报告 | `docs/versions/code-review-v{X.Y.Z}.md` | §7.3 审查后 | Phase 6 ③ C 步骤：文件必须存在 |
| 计划审计报告 | `docs/versions/plan-audit-report-V{x.y.0}.md` | plan-audit 完成后 | /mode-autocode Phase 1：计划状态为"已确认"才可执行 |
| 封板审计报告 | `docs/versions/seal-audit-vX.Y.md` | §1.10 封板检查 | Phase 8 前置条件：封板审计必须存在 |
| Phase 8 Stage 报告 | `docs/audits/v{X.Y.Z}/stage{1,2,3}-*.md` | Phase 8 各 Stage | Phase 8 ③ 门禁：三份报告齐全 |
| Phase 8 整合报告 | `docs/audits/v{X.Y.Z}/audit-report.md` | Phase 8 整合 | 版本收尾前置条件：审计报告存在且无 Critical |

### 修复时的编辑历史规则

当审计/审查发现问题并修复后，**不允许删除原报告重写**，必须在原文件内追加修订记录：

**格式**：

```markdown
---
## 修订历史

### 修订 1 — {YYYY-MM-DD HH:MM}
- **触发原因**：{Phase 8 Stage 2 发现 Critical / Code Review 发现 Important / ...}
- **修复内容**：
  - [Critical] {问题描述} → 已修复（{修复方式}）
  - [Important] {问题描述} → 已修复（{修复方式}）
- **重审结果**：{Stage 2 重审通过 / Code Review 确认修复}
- **修复 commit**：{commit hash}

### 修订 2 — {YYYY-MM-DD HH:MM}
...
```

**规则**：
1. 原始报告内容**不得修改或删除**（保留发现问题的原始记录）
2. 修复后的状态变更**只在修订历史中记录**
3. 每次修订必须记录：触发原因、修复内容、重审结果、commit hash
4. 修订历史追加在文件末尾，按时间正序排列

### 适用场景

| 场景 | 操作 |
|------|------|
| Phase 4 审计发现问题 → 修复 → 重审 | 在 task-report 末尾追加修订记录 |
| Code Review 发现 Critical → 修复 | 在 code-review 报告末尾追加修订记录 |
| Phase 8 Stage 发现 Critical → 修复 → 重审 | 在对应 stage 报告末尾追加修订记录 |
| 计划审计发现问题 → 修改计划 → 重审 | 在 plan-audit-report 末尾追加修订记录 |

### 为什么不允许覆盖

- 原始记录是**质量趋势分析的数据源**（Phase 8 整合 Agent 需要）
- 修订历史让未来的 Agent/开发者知道**这里曾经出过问题**
- 覆盖 = 销毁证据，违反可追溯性原则

## 方法论与 Phase 流程的映射

```
Phase 1（理解） ─── 无特殊方法论要求
Phase 2（编码） ─── §7.1 TDD（Red-Green-Refactor）
                    §7.5 并行子 Agent（独立任务时）
                    §7.4 Git Worktree（隔离开发时）
Phase 3（测试） ─── §7.1 TDD 产出的测试自然覆盖
Phase 4（审计） ─── §7.3 代码审查（审计后派发 reviewer）
Phase 5（汇报） ─── §7.7 报告强制归档
Phase 6（收尾） ─── §7.6 完成前验证 + §7.7 报告归档门禁
Phase 7（衍生） ─── 无特殊方法论要求
Phase 8（审计） ─── §7.3 + §7.6 + §7.7 联合应用

门禁失败修复 ────── §7.2 系统化调试（替代简单重试）
```
