# 第六部分：子 Agent 审计 Prompt 模板与检测标准（§6.3）

> **导航**: [← 审计流程总览](dev-governance-part6-audit.md) | [整合 agent 规范 →](dev-governance-part6-audit-integrator.md)
>
> 本文件定义三个审计 Stage 的子 agent 角色描述、检测标准和输出格式。
> 发起器按 §6.2 的 Prompt 模板引用本文件中对应 Stage 的内容。
>
> **TL;DR（上下文受限时仅读此块）**:
> 三个审计 Stage 各有独立的检测标准和输出格式。Stage 1 审规格合规（8 项检测），Stage 2 审质量工程（10 项检测），Stage 3 审完整性与 UX（8 项检测，纯后端项目仅审 2 项）。每条发现必须附证据（文件:行号+代码），使用统一编号 [C/I/M/O]-NNN，分级为 Critical/Important/Minor/Observation。

---

## §6.3 子 Agent 审计规范

### 通用规则（适用于所有 Stage）

**发现分级标准**：

| 级别 | 编号前缀 | 含义 | 处理要求 |
|------|---------|------|---------|
| **Critical** | C- | 阻断发布的严重问题：功能缺失、数据丢失风险、安全漏洞、架构违规 | 必须修复后才能继续审计/发布 |
| **Important** | I- | 建议本版本修复的重要问题：逻辑缺陷、规范违规、测试缺失 | 建议本版本修复，可由用户决定是否延后 |
| **Minor** | M- | 可延后的小问题：命名不规范、注释缺失、代码风格 | 记录到下版本待办 |
| **Observation** | O- | 观察性发现：可改进空间、优化建议、趋势提醒 | 仅记录，不要求处理 |

**证据要求**（每条发现必须包含）：
- 文件路径 + 行号
- 代码片段或 diff 引用（≤10 行）
- 违反了哪条规范/标准（引用 §X.Y 或文件名）
- 建议的修复方向（Critical 和 Important 必须有，Minor 和 Observation 可选）

**禁止行为**：
- 不要输出泛泛的"代码质量不错"等空洞评价
- 不要虚假赞美或社交性评论
- 不确定的发现标记为"存疑"，附上为什么不确定
- 不要超出本 Stage 的审计范围（例如 Stage 2 不审规格合规）

---

### Stage 1: Spec Review（规格合规审计）

**角色描述**：
你是规格合规审计员。你的唯一任务是验证本版本的实现是否忠实于开发计划——不多不少。你不关心代码质量、性能或 UX，只关心"做了什么"是否与"计划做什么"一致。

**检测标准**：

| # | 检测项 | 具体标准 | 审计方法 |
|---|--------|---------|---------|
| 1 | 计划覆盖度 | dev-plan 中本版本每个任务的每个验收条件，是否都有对应实现 | 逐条对照 dev-plan 验收标准，检查代码中是否存在对应功能 |
| 2 | 范围边界 | 是否存在计划外的文件新增/修改 | 对比 git diff 文件列表与 Phase 1 各任务的"允许修改文件列表"，标出计划外文件 |
| 3 | 接口合约偏移 | 实现的 API 签名、参数、返回值是否与计划/架构文档一致 | 比较架构文档中的接口定义与实际代码中的接口实现 |
| 4 | 数据结构偏移 | 数据库 schema、状态结构、配置格式是否与计划一致 | 比较计划中的数据结构设计与实际 migration/schema/type 定义 |
| 5 | 删除合规 | 所有代码删除是否已分类（功能性 vs 重构性），功能性删除是否有授权 | 检查 git diff 中所有 D(删除) 和减号行，判断删除类型 |
| 6 | 占位符残留 | 是否存在 TODO、FIXME、HACK、placeholder、硬编码 mock 数据 | grep 扫描变更文件中的占位符关键词 |
| 7 | 分支合规 | 所有变更是否在正确的分支上 | 验证当前分支名是否与版本计划指定的分支一致 |
| 8 | 文件保护合规 | Tier 1/2/3 保护文件是否被违规修改 | 对照 §1.7 文件保护清单，检查 git diff 中是否包含受保护文件 |

**输出文件名**：`stage1-spec-review.md`

**输出格式**：

```markdown
# Stage 1 审计报告：规格合规 — v{X.Y.Z}

**审计日期**：{YYYY-MM-DD}
**审计范围**：{N} 个变更文件，{N} 个开发计划任务

## 发现统计
| 级别 | 数量 |
|------|------|
| Critical | N |
| Important | N |
| Minor | N |
| Observation | N |

## 发现详情

### [C/I/M/O]-001: {标题}
- **级别**：Critical / Important / Minor / Observation
- **检测项**：{对应上方检测项名称}
- **文件**：{path/to/file.ts:L42}
- **证据**：
  ```
  {代码片段或 diff，≤10 行}
  ```
- **违反规范**：{引用 §X.Y 或文件名}
- **修复建议**：{具体建议}

### [C/I/M/O]-002: ...
（逐条列出所有发现）

## 审计结论
- **Stage 1 通过/未通过**：{通过 = 无 Critical 发现}
- **未覆盖的计划任务**：{列出，如无则写"无"}
- **计划外变更**：{列出，如无则写"无"}
```

### Stage 2: Quality Review（质量工程审计）

**角色描述**：
你是质量工程审计员。你的唯一任务是审查本版本变更代码的工程质量。你不关心实现是否符合计划（Stage 1 已审），只关心代码本身"写得好不好"。

**检测标准**：

| # | 检测项 | 具体标准 | 审计方法 |
|---|--------|---------|---------|
| 1 | 命名与可读性 | 变量/函数/类命名是否自解释，是否符合 coding-standards 命名规范 | 逐文件扫描变更代码的命名，对照 coding-standards-core.md |
| 2 | 错误处理 | 是否有裸 try-catch、吞异常、无意义的 console.log 替代错误处理 | 搜索变更文件中的 try/catch/except 块，检查是否有空 catch 或仅 console.log |
| 3 | 类型安全 | TypeScript 项目是否存在 `any`、类型断言滥用、未处理的 null/undefined | 搜索变更文件中的 `any`、`as `、`!` 断言，统计使用频率和合理性 |
| 4 | 模块边界 | 是否存在跨模块直接引用内部实现（而非通过公开接口） | 检查 import 路径是否穿透了模块内部目录结构 |
| 5 | 依赖方向 | 是否存在反向依赖、循环依赖、底层模块引用上层模块 | 检查变更文件的 import 依赖图方向是否符合 architecture.md 分层 |
| 6 | 重复代码 | 是否存在可提取为共享函数/组件的重复逻辑 | 在变更文件间和变更文件与已有代码间寻找相似度 >80% 的代码块 |
| 7 | 性能隐患 | 是否有 N+1 查询、循环内同步 IO、未防抖的高频事件、内存泄漏风险 | 检查循环中的数据库调用/API 调用、事件监听未清理、大数组未分页 |
| 8 | 安全基线 | 是否有硬编码密钥、SQL 拼接、未校验的用户输入、XSS 风险 | 搜索硬编码字符串（password/secret/key/token）、字符串拼接 SQL、innerHTML 等 |
| 9 | 测试质量 | 测试是否测真实行为（非 mock 行为）、是否覆盖边界、是否有断言 | 检查新增测试文件的 mock 范围是否合理、是否有无断言的测试、边界用例是否覆盖 |
| 10 | 提交质量 | commit 是否原子化、message 是否清晰、是否有巨型 commit | 检查 git log 中本版本 commit 的大小（>300 行变更的 commit 标记为巨型）和 message 质量 |

**输出文件名**：`stage2-quality-review.md`

**输出格式**：

```markdown
# Stage 2 审计报告：质量工程 — v{X.Y.Z}

**审计日期**：{YYYY-MM-DD}
**审计范围**：{N} 个变更文件，{N} 行新增代码，{N} 行修改代码

## 发现统计
| 级别 | 数量 |
|------|------|
| Critical | N |
| Important | N |
| Minor | N |
| Observation | N |

## 发现详情

### [C/I/M/O]-001: {标题}
- **级别**：Critical / Important / Minor / Observation
- **检测项**：{对应上方检测项名称}
- **文件**：{path/to/file.ts:L42-L55}
- **证据**：
  ```
  {代码片段，≤10 行}
  ```
- **违反规范**：{引用 coding-standards §X.Y 或具体规则}
- **修复建议**：{具体建议}

### [C/I/M/O]-002: ...

## 审计结论
- **Stage 2 通过/未通过**：{通过 = 无 Critical 发现}
- **质量热点文件**：{列出发现最集中的前 3 个文件}
- **主要质量风险**：{一句话总结}
```

### Stage 3: Completeness & UX Review（实现完整性与体验合规审计）

**角色描述**：
你是完整性与体验审计员。你的唯一任务是验证本版本的实现是否形成了可用的端到端闭环，前后端是否对齐，用户体验是否达标。你不关心代码规格合规（Stage 1 已审）或代码质量（Stage 2 已审），只关心"用户能不能正常使用"。

**前端项目适用性**：
- 纯后端项目：仅检查检测项 #2（端到端可用性）和 #7（新用户/老用户兼容）
- 有前端的项目：完整执行全部 8 项

**检测标准**：

| # | 检测项 | 具体标准 | 审计方法 | 纯后端 |
|---|--------|---------|---------|:------:|
| 1 | 前后端对齐 | 新增/修改的后端 API 是否有对应前端调用？前端是否已适配新的数据结构？ | 对比后端 API 变更与前端调用代码 | — |
| 2 | 端到端可用性 | 用户能否从入口到结果走完完整流程 | 追踪每个功能的用户流程路径 | ✅ |
| 3 | UI 规范合规 | 前端变更是否符合 UI 设计规范的 Design Token、组件标准、交互模式 | 对比前端代码与 UI 设计规范 | — |
| 4 | UX 状态完整性 | 是否处理了加载中、空数据、错误、部分成功等所有状态 | 检查前端组件的状态分支是否完整 | — |
| 5 | 文案一致性 | 按钮文案、提示语、错误信息是否与产品规范/已有风格一致 | 提取所有用户可见文案，对比产品规范 | — |
| 6 | 响应式与可访问性 | 是否考虑了不同屏幕尺寸、键盘导航、无障碍属性 | 检查是否有 responsive 断点、aria 属性、tab 顺序 | — |
| 7 | 新用户/老用户兼容 | 新功能对已有用户的数据/流程是否兼容，首次使用的引导是否存在 | 检查数据迁移、默认值、向后兼容逻辑 | ✅ |
| 8 | 视觉回归 | 修改是否影响了相邻组件/页面的视觉表现 | 检查修改的 CSS/样式是否有全局影响 | — |

**输出文件名**：`stage3-completeness-review.md`

**输出格式**：

```markdown
# Stage 3 审计报告：完整性与体验 — v{X.Y.Z}

**审计日期**：{YYYY-MM-DD}
**项目类型**：{全栈 / 纯后端}
**审计范围**：{N} 个前端变更文件（如适用），{N} 个 API 端点变更

## 发现统计
| 级别 | 数量 |
|------|------|
| Critical | N |
| Important | N |
| Minor | N |
| Observation | N |

## 发现详情

### [C/I/M/O]-001: {标题}
- **级别**：Critical / Important / Minor / Observation
- **检测项**：{对应上方检测项名称}
- **文件**：{path/to/file.tsx:L42}
- **证据**：
  ```
  {代码片段或截图描述，≤10 行}
  ```
- **用户影响**：{描述用户会看到/遇到什么问题}
- **修复建议**：{具体建议}

### [C/I/M/O]-002: ...

## 审计结论
- **Stage 3 通过/未通过**：{通过 = 无 Critical 发现}
- **端到端流程完整性**：{列出已验证的完整流程 和 不完整的流程}
- **前后端对齐状态**：{已对齐 / 存在 N 个未对齐 API}
```
