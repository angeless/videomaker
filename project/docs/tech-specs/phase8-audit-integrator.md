> 本文件定义整合 agent 的职责、输入输出规范，以及审计报告的归档结构。

> **TL;DR（上下文受限时仅读此块）**:
> 整合 agent 读取三份 Stage 审计报告 + 上一版本审计报告（如有）+ CHANGELOG + memory，输出版本审计报告。核心职责：合并去重、分级定性（Critical/Important/Minor/Observation）、趋势分析（与上一版本对比）、健康度评分（A-F）、修复建议。每条"通过"判定必须附证据引用。报告归档到 `docs/audits/v{X.Y.Z}/`。

## §6.4 整合 Agent 规范

### 角色描述

你是版本审计整合员。你的任务是将三个独立审计 Stage 的报告合并为一份统一的版本审计报告。你不直接审计代码，而是基于三份审计报告进行交叉验证、去重、定性和趋势分析。

### 输入材料

| 材料 | 来源 | 用途 |
|------|------|------|
| Stage 1 审计报告 | 规格合规子 agent | 主要输入 |
| Stage 2 审计报告 | 质量工程子 agent | 主要输入 |
| Stage 3 审计报告 | 完整性与 UX 子 agent | 主要输入 |
| 上一版本 `audit-report.md` | `docs/audits/v{上一版本}/` | 趋势对比（首次审计时无此输入） |
| CHANGELOG.md（本版本条目） | 项目根目录 | 背景上下文 |
| memory（`.auto-memory/`） | 项目记忆 | 项目历史上下文 |

### 整合逻辑

**第一步：合并去重**
- 不同 Stage 发现的同一问题（同一文件同一行号或同一功能缺陷），合并为一条
- 标注"多维度发现"（如"本发现由 Stage 1 + Stage 2 同时识别"）
- 多维度发现的级别取最高级（如 Stage 1 标 Important，Stage 2 标 Critical，最终定为 Critical）

**第二步：分级定性**
- 保持各 Stage 子 agent 的原始定级，仅在以下情况调整：
  - 多维度发现取最高级（如上）
  - 子 agent 明确标注"存疑"的发现，整合 agent 结合其他 Stage 的证据做最终判定
  - 如果整合 agent 无法确定级别，保留"存疑"标记，不强行定级
- 如果两个 Stage 对同一文件/同一功能得出相反结论（一个认为合规，一个认为违规），标记为"冲突待裁决"（conflict-review-required），在整合报告中单独列出，不自动定级

**第三步：趋势分析**（仅在上一版本审计报告存在时执行）
- **已修复**：上一版本存在但本版本不再出现的问题（匹配规则：同文件同检测项或同编号）
- **新增**：本版本首次出现的问题
- **持续存在**：跨版本未修复的问题（标注持续版本数）
- **恶化**：严重级别升高的问题（如 Minor → Important）

**第四步：健康度评分**

| 评分 | 条件 |
|------|------|
| **A** | 0 Critical，0 Important，≤3 Minor |
| **B** | 0 Critical，≤3 Important，任意 Minor |
| **C** | 0 Critical，>3 Important |
| **D** | 1-2 Critical（已有修复建议） |
| **F** | ≥3 Critical 或任何 Critical 无修复建议 |

**第五步：修复建议与下版本关注点**
- 针对每个 Critical 和 Important 发现，整合三个 Stage 的修复建议，给出最终建议
- 提炼下个版本需要重点关注的事项（基于本次发现的模式和趋势）

### 证据引用要求

> **硬规则**：整合报告中每一条判定都必须附上证据引用。

- **发现类判定**：引用子 agent 报告中的具体编号和证据（如"见 Stage 2 [I-003]"）
- **"通过"类判定**：引用子 agent 报告中"无发现"的结论，或引用检测通过的具体文件/行号范围
- **趋势类判定**：引用上一版本报告编号和本版本对应项

禁止：
- 空 ✓（没有证据的通过标记）
- "未发现问题"（必须说明检查了什么范围，在哪些文件/模块中未发现）

### 整合报告输出格式

```markdown
# 版本审计报告 v{X.Y.Z}

- **版本号**：v{X.Y.Z}
- **分支**：test-v-{X}-{Y}

| 级别 | 数量 | 多维度发现 |

- **发现来源**：Stage {N}（{Stage 名称}）{+ Stage {M} 如多维度}

- **相比 v{上一版本}**：
  - 已修复：{N} 项（{列出关键项}）
  - 新增：{N} 项（{列出关键项}）
  - 持续存在：{N} 项（{列出及持续版本数}）

3. ...

## 各维度审计详情
> 详见同目录下各 Stage 原始报告：
> - [Stage 1: 规格合规](stage1-spec-review.md)
```

## §6.5 审计报告归档规范

### 归档目录结构

```
docs/
└── audits/
    ├── audit-index.md              ← 跨版本索引（每次审计后更新）
    ├── v1.0.0/
    │   ├── audit-report.md         ← 整合报告
    │   ├── stage1-spec-review.md   ← Stage 1 原始报告
    │   ├── stage2-quality-review.md← Stage 2 原始报告
    │   └── stage3-completeness-review.md ← Stage 3 原始报告
    ├── v1.1.0/
    │   └── ...
    └── v{X.Y.Z}/
        └── ...
```

### 归档操作步骤

1. 创建 `docs/audits/v{X.Y.Z}/` 目录
2. 保存三份 Stage 审计报告为对应文件名
3. 保存整合报告为 `audit-report.md`
4. 更新 `docs/audits/audit-index.md`

### audit-index.md 格式

```markdown
# 版本审计索引

| 版本 | 审计日期 | 健康度 | Critical | Important | Minor | 趋势 |
|------|---------|--------|----------|-----------|-------|------|
| v{X.Y.Z} | {YYYY-MM-DD} | {A-F} | {N} | {N} | {N} | {↑改善/→持平/↓恶化} |
| v{prev} | {YYYY-MM-DD} | {A-F} | {N} | {N} | {N} | — |

## 各版本审计报告
- [v{X.Y.Z} 审计报告](v{X.Y.Z}/audit-report.md)
- [v{prev} 审计报告](v{prev}/audit-report.md)
```

### 首次审计特殊处理

- 没有上一版本审计报告时，趋势列填"基线"
- 整合报告中的趋势分析章节标注"本次为基线审计，无历史对比"
- 本次报告自动成为后续版本的对比基线
