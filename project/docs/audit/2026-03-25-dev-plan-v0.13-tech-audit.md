## 三、高严重度冲突详情

### C1 + C2 + C3：R2 退化日志与现有基础设施冲突

**计划描述**：
- 在 `audit_log.py` 中新增 `log_degradation(module, reason, fallback_path, severity)` 函数
- 写入 `~/.videoeditor/logs/degradation.jsonl`（JSONL 格式，每行一条记录）
- 新增 `GET /api/system/degradation-log` 端点查询此日志

**实际代码状况**：

```
# modules/app_api/services/audit_log.py 已有：
def audit(
    operation: str,
    resource_type: str,
    resource_id: Optional[str] = None,
    *,
    actor: str = "unknown",
    status: str = "ok",
    detail: Optional[Dict[str, Any]] = None
) -> None:
    # 写入 SQLite，表结构：(id, operation, resource_type, resource_id, actor, status, detail_json, created_at)

# modules/app_api/routes/system_routes.py 已有：
GET /api/system/audit   # 支持 ?operation=&status=&limit= 过滤，返回最近 N 条记录
```

**冲突分析**：

| 维度 | 计划方案 | 现有基础设施 | 冲突程度 |
|------|---------|------------|---------|
| 存储介质 | JSONL 文件 | SQLite | 🔴 重复建设 |
| 文件路径 | `~/.videoeditor/logs/degradation.jsonl`（硬编码） | coding-standards §9：路径须从配置读取 | 🔴 规范违反 |
| 查询接口 | `GET /api/system/degradation-log` | `GET /api/system/audit?operation=degradation` | 🔴 功能重复 |
| 写入函数 | `log_degradation(module, reason, ...)` | `audit("degradation", module, ...)` | 🔴 功能重复 |

**推荐修正方案**：

删除新建 `log_degradation()` 计划，改为调用现有 `audit()`：

```python
# 在 workflow.py 退化点处调用：
audit(
    operation="degradation",
    resource_type=module_name,        # e.g. "step2_subtitle"
    resource_id=None,
    actor="workflow_engine",
    status="degraded",
    detail={
        "reason": reason_str,
        "fallback_path": fallback_path,
        "severity": "warning"         # or "error"
    }
)
```

查询端无需新建端点，直接用：
```
GET /api/system/audit?operation=degradation&limit=100
```

R2 涉及文件表改为：

| 文件 | 动作 | 说明 |
|------|------|------|
| `modules/workflow_engine/workflow.py` | Modify | 在 3 个退化点调用 `audit()` 替代 `logger.warning()` |
| `modules/app_api/services/audit_log.py` | **不变** | 现有基础设施已满足需求，无需修改 |
| `modules/app_api/routes/system_routes.py` | **不变** | `GET /api/system/audit` 已可查询退化记录 |

### C4：R11 MCP 工具映射表 4 条端点路径错误

**计划描述**（R11 MCP 工具映射表）：

| 工具名 | 计划路径 | 实际路径 | 状态 |
|--------|---------|---------|------|
| `agent_task_run` | `POST /api/agent/task/run` | `POST /api/agent/tasks/run` | 🔴 错误（singular→plural） |
| `workflow_run` | `POST /api/workflow/run` | `POST /api/workflows/run` | 🔴 错误（缺 s） |
| `library_ingest` | `POST /api/library/ingest-local` | `POST /api/library/ingest/local` | 🔴 错误（连字符→路径分隔符） |
| `project_list` | `GET /api/legacy/projects` | `GET /api/projects` | 🔴 错误（多余 /legacy 前缀） |

**核查依据**：
- `agent_task_run`：见 `modules/app_api/routes/agent_task_run_routes.py` → `@bp.route("/tasks/run", methods=["POST"])`，Blueprint prefix `/api/agent`
- `workflow_run`：见 `modules/app_api/routes/workflow_routes.py` → `@bp.route("/workflows/run", ...)` 或 Blueprint prefix 含复数
- `library_ingest`：见 `modules/app_api/routes/library_routes.py` → `POST /api/library/ingest/local`（路径分隔符）
- `project_list`：见 `modules/app_api/routes/legacy_project_routes.py` → 注册为 `/api/projects`，无 `/legacy/` 前缀

**推荐修正**：将 R11 MCP 工具映射表中以上 4 条路径全部更正为实际路径。

## 四、中严重度冲突详情

### C5：R8/R9 导出路由不符合 capabilities 命名约定

**计划路径**：
- `POST /api/export/jianying`
- `POST /api/export/fcpxml`

**规范要求**（`architecture.md §3.7`）：
> 所有能力类路由均使用 `/api/capabilities/<name>/...` 前缀

**现有 capability 路由示例**（`capability_editing_routes.py`）：
```
POST /api/capabilities/smart_cut/run
POST /api/capabilities/auto_subtitle/run
POST /api/capabilities/color_grade/run
```

**推荐修正**：
```
POST /api/capabilities/jianying_export/run
POST /api/capabilities/fcpxml_export/run
```

对应路由文件命名建议：`capability_export_routes.py`

**计划路径**：
- `POST /api/beauty/preview`

### C7：R7 引入 `{project_id}` 与现有 timeline 路由风格不一致

**现有端点**（无 project_id）：
```
GET  /api/timeline
POST /api/timeline/edit-by-prompt
POST /api/timeline/reorder
POST /api/timeline/trim
```

**计划新增**（有 project_id）：
```
GET /api/timeline/{project_id}/tracks
PUT /api/timeline/{project_id}/tracks
```

**风险**：引入 `{project_id}` 后，前端需要同时处理两套 URL 模式，增加维护复杂度；且若现有端点依赖 session/global state 而非 project_id 参数，新旧接口语义可能不一致。

**推荐处理**：在 R7 已知约束中补充说明：
> "当前 timeline 端点均为无状态会话模式，`{project_id}` 参数由调用方在请求体中传入，不体现在 URL 路径中。新端点应沿用 `POST /api/timeline/tracks-update { project_id, tracks }` 风格，保持与现有端点一致。"

若产品确需引入 project_id 路径参数，应在 R7 之前增加一个独立任务，统一升级现有端点，而非仅新端点使用新风格。

---

### C8：R4 `compact_if_needed()` 挂载点在现有代码中不存在

**计划描述**：在 `global_media_library.py` 的现有方法中挂载 `compact_if_needed()` 调用。

**实际状况**：`global_media_library.py` 当前无 `_refresh_cache()`、`rebuild_index()`、`add_batch()` 等可作为 compact hook 的方法入口。`compact_if_needed()` 的触发时机（`_deleted` 比例 > 20%）需要在 `VectorIndex.add_batch()` 或 `VectorIndex.delete()` 之后判断。

**推荐处理**：R4 Phase 1 实施计划中补充：
> "首先在 `vector_index.py` 的 `add_batch()` 和 `delete()` 方法末尾确认合适的 compact 触发点，再在 `global_media_library.py` 的相应调用链中挂载。若无现成调用链，需新增一个包装方法。"

## 五、低严重度问题

### C9：R11 `modules/mcp_server/` 模块归属

`architecture.md` 将 `modules/` 定义为业务模块区，`apps/` 为应用入口区。MCP Server 本质上是一个独立运行的服务入口（类似 `apps/desktop/`），放在 `modules/` 下与架构语义不符。

**建议**：考虑 `apps/mcp_server/`，但若团队偏好将 MCP 视为内嵌服务模块保留在 `modules/`，需在 ADR 中记录决策依据。当前评审不阻断开发。

---

### C10：R12 E2E 测试文件命名

计划文件名：`test_e2e_r1_seed.py`、`test_e2e_r11_mcp.py`（任务ID前缀）

`testing-strategy.md §5.1` 推荐场景式命名：`test_e2e_<scenario>.py`

建议改为：`test_e2e_seed_library.py`、`test_e2e_mcp_server.py` 等，提升可读性。若坚持任务ID命名，需在 testing-strategy 中补充"v0.13 专项测试可使用任务ID命名"注记。
