# 2. 系统定位

这是一个 **帮助识别本地视频和图片语义** 的软件，不是一个 AI 生成视频的软件。

核心能力不是“创作”，而是：

1. 识别图片和视频中的语义信息
2. 自动打标签
3. 支持用自然语言或关键词进行检索
4. 支持用户添加自定义关键词
5. 支持系统根据用户反馈持续扩展语义能力

因此，这套系统的重点不是视频生成模型，而是：

- 视觉识别
- OCR 文本识别
- ASR 语音识别
- 标签词库
- 语义归一化
- 规则推理
- 多证据融合
- 用户反馈学习

---

# 3. 核心设计判断：问题不只是“词太少”，更是“词库结构太平”

当识别效果不好时，很多人会本能地觉得：

> 词库太小了，再多加一点词就好了。

但实际上，效果不好的原因通常不只是词少，而是下面这些问题：

1. 词库只有平铺列表，没有层级
2. 没有把“地点 / 场景 / 物品 / 人物 / 动作 / 时间 / 天气 / 风格 / 抽象主题”拆开
3. 没有别名映射与同义词归一
4. 没有做复合语义推理
5. 没有做负向排除
6. 视频逐帧判断，没有做时间窗口聚合
7. 用户自定义词直接污染主库
8. 自动学习没有审核闭环

所以真正有效的设计不是“只有一个大词表”，而是：

**层级标签库 + 同义词映射 + 复合规则 + 自定义词 + 学习候选池 + 反馈闭环**

---

# 4. 这套方案的总体结构

整套能力建议拆成 4 层：

## 4.1 基础词库层
负责回答：

- 有哪些标签
- 标签属于什么分类
- 标签之间是什么关系
- 哪些词是别名、口语、同义表达

## 4.2 识别证据层
负责收集所有可能的语义证据：

- 视觉模型识别到的物体
- 场景分类结果
- 动作识别结果
- OCR 识别出的文字
- ASR 识别出的语音文本
- 文件名 / 文件夹名 / EXIF / GPS / 时间等元数据

## 4.3 决策融合层
负责把来自不同来源的证据合并，做：

- 同义词归一
- 别名映射
- 父子标签传播
- 复合语义推理
- 负向规则排除
- 冲突处理
- 分数融合
- 视频时序平滑

## 4.4 学习扩展层
负责处理：

- 用户新增自定义关键词
- 系统发现的高频新词
- 审核后升级成正式别名或正式标签
- 用户反馈纠错
- 词库版本管理

# 5. 为什么不能只做“一个大词表”

因为同一个画面里，其实会同时存在多个维度：

例如一张图里有：

- 厨房（地点）
- 做饭（场景/动作）
- 母亲（人物）
- 锅（物品）
- 晚上（时间）
- 暖光（视觉风格）
- 家庭生活（抽象语义）

如果只输出一个标签，比如“做饭”，就浪费了大量可检索信息。

更合理的输出应该是多标签并行：

```text
地点: 厨房
场景: 家庭做饭
人物: 母亲 / 女性
动作: 切菜 / 烹饪
物品: 锅 / 刀 / 砧板 / 冰箱
时间: 夜晚
风格: 暖光 / 生活化
抽象语义: 家庭生活 / 陪伴感
```

这也是为什么你的软件更适合设计成 **多通道标签系统**，而不是单一标签系统。

# 6. 词库总体设计原则

1. 不要只做平面关键词列表，必须做层级结构。
2. 同一素材要支持多标签输出。
3. 同义词、别名、口语必须归一到标准标签。
4. 复合语义不要靠穷举关键词，而要靠规则组合。
5. 用户自定义词必须带父类，不能是孤立词。
6. 自动学习的新词不能直接进主库，必须先进入待审核池。
7. 视频不要逐帧硬判，必须做镜头段与时间窗口聚合。
8. 每个标签尽量保留“它为什么出现”的证据链，方便解释与纠错。
9. 正式系统词库与用户自定义词库必须隔离。
10. 将来即使替换底层视觉模型，也不应推翻这套词库和数据结构。

# 8. 顶层分类建议

建议使用以下 12 个顶层分类：

1. 地点
2. 场景
3. 物品
4. 人物
5. 动作
6. 时间与环境
7. 动物
8. 植物
9. 交通与建筑
10. 视觉风格
11. 文本与媒体
12. 抽象语义

这套分类的好处是：

- 能覆盖大多数图片和视频常见表达
- 适合多标签并行输出
- 适合做自然语言检索
- 适合后续继续扩充
- 既适合图片，也适合视频

# 9. 每个标签建议包含的字段

不要只存一个词名。每个关键词最好包含以下字段：

| 字段 | 说明 |
|---|---|
| tag_id | 标签唯一 ID |
| tag_name | 标准标签名 |
| tag_type | 标签类型，如地点/物品/动作 |
| top_category | 顶层分类 |
| subcategory | 子分类 |
| parent_id | 父标签 ID |
| level | 层级深度 |
| aliases | 别名/口语/常见俗称 |
| synonyms | 同义表达 |
| related_tags | 相关词 |
| negative_tags | 负向排除词 |
| trigger_objects | 可触发该标签的物体 |
| trigger_scenes | 可触发该标签的场景 |
| trigger_texts | OCR / ASR 可触发文本 |
| score_threshold | 标签生效阈值 |
| is_custom | 是否用户自定义 |
| allow_auto_expand | 是否允许自动扩展 |
| is_active | 是否启用 |
| review_status | 审核状态 |
| created_by | 系统/用户/运营 |
| source | 来源 |

# 10. 标签之间的关系类型

标签不仅仅是独立存在的，还存在关系。建议至少支持以下关系：

1. **parent_of / child_of**：父子层级关系
2. **alias_of**：别名映射关系
3. **synonym_of**：同义关系
4. **related_to**：相关语义关系
5. **conflict_with**：冲突/互斥关系
6. **cooccur_with**：高频共现关系
7. **trigger_for**：可触发更高层标签的关系

例如：

- 锅 → trigger_for → 做饭
- 黑板 → trigger_for → 教室
- 沙滩 → cooccur_with → 海浪
- 白大褂 → trigger_for → 医疗场景
- 羽毛球 → conflict_with → 网球

# 11. 为什么要做同义词与别名映射

因为用户、模型、OCR、ASR 输出的词不可能完全统一。

例如：

- 电动车 / 电瓶车 / 电摩 / 电单车
- 便利店 / 小卖部 / 便利商店
- 客厅 / 起居室
- 卫生间 / 厕所 / 洗手间 / WC

如果没有别名映射，就会出现：

- 识别明明是对的，但检索搜不到
- 标签重复、脏乱
- 相似内容无法聚合

所以建议：

- 所有展示层统一显示“标准标签名”
- 用户搜索时可用别名命中标准标签
- 识别结果先归一，再落库

---

# 12. 为什么要做复合语义规则

很多高层语义不是靠单个物体就能确定的。

例如：

- 看到“锅”不一定就是做饭
- 看到“白大褂”不一定就是医生
- 看到“篮球”不一定就是比赛

但如果多个证据同时出现，就更可信：

- 锅 + 灶台 + 冰箱 → 厨房
- 锅 + 砧板 + 切菜 + 围裙 → 做饭
- 白大褂 + 听诊器 + 诊室 → 医疗 / 医生
- 麦克风 + 舞台灯 + 观众 → 演出现场

所以复合语义规则是这个系统准确率的重要来源。

# 13. 复合标签模板

建议用模板式规则，而不是穷举所有词组合。

## 13.1 基础描述模板

时间段 + 天气 + 地点 + 人物 + 动作 + 物品

例：

- 傍晚 + 雨天 + 城市街道 + 年轻女性 + 行走 + 雨伞

## 13.2 场景归纳模板

地点 + 场景 + 人物 + 关键物品

例：

- 厨房 + 做饭 + 母亲 + 锅 / 刀 / 砧板

## 13.3 旅行视频模板

地点 + 时间段 + 天气 + 人物 + 行为 + 镜头

例：

- 海边 + 日落 + 晴天 + 游客 + 打卡拍照 + 航拍

## 13.4 职业识别模板

人物职业 + 服装 + 动作 + 专属物品 + 地点

例：

- 医生 + 白大褂 + 问诊 + 听诊器 + 诊室

## 13.5 体育模板

运动场地 + 人物 + 动作 + 器材 + 比赛状态

例：

- 篮球场 + 运动员 + 投篮 + 篮球 + 比赛

## 13.6 电商展示模板

产品 + 人物 + 动作 + 风格 + 文本媒体

例：

- 护肤品 + 主播 + 讲解 + 商业广告风 + 字幕

## 13.7 安全事件模板

风险主题 + 地点 + 动作 + 应急物品 + 人物

例：

- 火灾风险 + 工厂车间 + 灭火 + 灭火器 + 消防员

## 13.8 亲子模板

家庭角色 + 儿童状态 + 动作 + 玩具 + 地点

例：

- 母亲 + 儿童 + 陪伴 + 积木 + 客厅

## 13.9 宠物模板

动物 + 动作 + 道具 + 地点 + 氛围

例：

- 狗 + 奔跑 + 牵引绳 + 公园 + 欢乐

## 13.10 镜头语言模板

主体 + 景别 + 镜头运动 + 光照 + 氛围

例：

- 歌手 + 特写 + 推镜 + 舞台灯光 + 紧张

# 14. 负向规则为什么重要

有些标签很容易误判，因此需要负向排除词或冲突关系。

示例：

- 命中 听诊器 + 白大褂 时提升“医生”
  - 但若同时命中：角色扮演 / 万圣节装扮，则应扣分

- 命中 球拍 + 球网 + 击球 时提升“网球”
  - 若命中 羽毛球，则应冲突扣分

- 命中 舞台灯 + 麦克风 + 观众 时提升“演出现场”
  - 若只是直播背景灯，不一定是线下演出

因此，负向规则能显著减少“看起来像但其实不是”的误识别。

# 15. 图片与视频应该共用一套结构

原因很简单：

1. 图片可以看成只有一个 segment 的视频
2. 视频本质上只是多帧、多时间段图片
3. 两者语义维度是一致的
4. 共用结构后，检索、标签、统计和 UI 都更统一

建议：

- 图片：只保留一个全局 segment
- 视频：支持多个 segment（镜头段/时间段）
- 全部使用统一的标签、证据、结果表结构

这样后期维护成本会低很多。

---

# 16. 视频为什么不能逐帧硬判

因为视频语义往往跨帧、跨时间段存在。

例如：

- 某一帧里看不到锅，但前后几帧都在做饭
- 某一帧人物背过身，识别不到职业
- OCR 文字只在 2 秒里闪过
- 某个动作需要连续几帧才成立

所以视频建议这样处理：

1. 先做镜头切分或固定时间窗切分
2. 每个 segment 内多帧采样
3. 汇总 segment 级标签
4. 再由多个 segment 聚合出全片标签

这样比逐帧打标签更稳定。

# 17. 推荐系统架构

```text
本地图片/视频
   ↓
帧抽样 / 镜头切分 / 音频抽取
   ↓
基础识别
   ├─ 视觉检测（物体 / 场景 / 人脸 / 动作）
   ├─ OCR（屏幕文字 / 路牌 / 海报 / 包装）
   ├─ ASR（视频语音 / 对白 / 解说）
   ├─ Metadata（拍摄时间 / GPS / 文件夹名 / 文件名）
   ↓
语义归一化
   ├─ 同义词映射
   ├─ 别名映射
   ├─ 复合规则推理
   ├─ 负向规则排除
   ↓
标签打分
   ├─ 单标签置信分
   ├─ 父子标签传播
   ├─ 时序平滑
   ├─ 多证据融合
   ↓
结果落库
   ├─ 资源表
   ├─ 标签表
   ├─ 识别结果表
   ├─ 自定义词表
   ├─ 待学习新词表
   ↓
用户反馈
   ├─ 确认正确
   ├─ 确认错误
   ├─ 新增别名
   ├─ 新增自定义词
   ↓
扩展学习 / 审核入库
```

# 18. 数据库建模建议

建议至少有下面这些表：

## 18.1 词库主数据表

### tag_category
存顶层分类，例如：地点、场景、物品、人物、动作。

### tag
标准标签主表。

### tag_alias
存别名、俗称、口语、同义词入口。

### tag_relation
存父子关系、相关关系、冲突关系、共现关系、触发关系。

### composite_rule
存复合语义规则，例如：

- 锅 + 灶台 + 冰箱 → 厨房
- 电脑 + 会议室 + 投影仪 → 开会 / 办公

## 18.2 媒体资源表

### asset
媒体文件主表，存图片/视频基本信息。

### asset_segment
视频镜头段 / 时间段；图片可只保留一条全局记录。

### evidence
原始识别证据表，记录“这个标签为什么出现”。

### asset_tag_result
最终标签结果表，记录融合后的标签分数。

## 18.3 用户扩展与学习表

### custom_tag
用户自定义标签主表。

### custom_tag_mapping
用户自定义词和系统词之间的映射关系。

### learning_candidate
自动学习发现的新词候选池。

### feedback_event
用户反馈日志。

### tag_version_log
词库版本记录和审计日志。

# 20. 标签打分核心思想

不要把模型输出直接当最终答案。

建议用下面这种融合思路：

```text
最终分 = 基础模型分 × 证据权重 × 规则修正 × 时序修正 × 用户修正
```

更工程化一点，可写成：

```text
final_score =
  clamp(
    base_score
    + source_bonus
    + cooccurrence_bonus
    + hierarchy_bonus
    + custom_boost
    - conflict_penalty
    - negative_penalty
    + temporal_smooth,
  0, 1)
```

---

# 21. 打分时各部分代表什么

## 21.1 base_score
来自单个模型或单条规则本身的分数：

- 视觉检测：0 ~ 1
- 场景分类：0 ~ 1
- OCR 文本命中：0 ~ 1
- ASR 文本命中：0 ~ 1
- 元数据匹配：0 ~ 1

## 21.2 source_bonus
不同来源可信度不同，可做修正：

| 证据源 | 建议权重 |
|---|---:|
| 视觉目标检测 | 1.00 |
| 场景分类 | 0.95 |
| 动作识别 | 0.95 |
| OCR 文本命中 | 0.75 |
| ASR 文本命中 | 0.72 |
| 文件名 / 文件夹名 | 0.45 |
| EXIF/GPS/拍摄时间 | 0.55 |
| 用户历史确认 | 1.10 |
| 自定义规则直接命中 | 1.15 |

## 21.3 cooccurrence_bonus
多个标签共现时，为更高层标签加分：

- 沙发 + 茶几 + 电视 → 客厅
- 床 + 衣柜 + 台灯 → 卧室
- 锅 + 燃气灶 + 冰箱 → 厨房
- 黑板 + 课桌 + 学生 → 教室
- 雪地 + 羽绒服 + 呼气白雾 → 冬季

## 21.4 hierarchy_bonus
子标签高分命中时，父标签可获得传播分：

- 厨房 → 室内居住空间
- 篮球比赛 → 体育与竞技
- 海边日落 → 自然风景 / 黄昏

建议：

- 子 → 父传播系数：0.18 ~ 0.35
- 父 → 子只做弱提示：0.03 ~ 0.08

## 21.5 conflict_penalty
互斥标签同时高分时扣分，例如：

- 白天 vs 夜晚
- 室内 vs 户外
- 雨天 vs 晴天
- 羽毛球 vs 网球
- 冬季雪景 vs 夏季海边

## 21.6 negative_penalty
负向排除词命中时扣分。

## 21.7 temporal_smooth
只用于视频：

- 邻近 segment 都出现时加分
- 只在一帧孤立出现时降权

# 22. 证据层为什么重要

建议每个最终标签都保留证据链。

例如一个“厨房”标签，不应该只是存一个分数，还应该知道：

- 视觉模型识别到：锅、灶台、冰箱
- 场景模型识别到：室内厨房
- OCR 没命中
- ASR 命中“准备做饭”
- 规则触发：锅 + 灶台 + 冰箱 → 厨房

这样做的好处：

1. 可解释
2. 容易调试
3. 容易做用户反馈
4. 容易纠错
5. 将来换模型时更稳

# 23. 用户自定义关键词机制

这是你系统里非常重要的一部分。

因为再大的系统词库，也无法完全覆盖用户的个性化需求。

例如用户可能想加：

- 露营氛围灯
- 北欧奶油风客厅
- 自家猫咪名字
- 某个品牌包装风格
- 自己定义的素材项目分类

因此建议支持用户自定义关键词。

但要注意：

**用户自定义词不要直接写入系统主库。**

而是应该：

- 单独存放
- 可以映射到系统标签
- 允许灰度生效
- 可以通过用户反馈逐步增强

---

# 24. 自定义关键词推荐字段

建议每个自定义词至少包含：

- 主关键词
- 别名
- 父分类
- 父标签
- 相关词
- 负向排除词
- 触发物体
- 触发场景
- 触发文本
- 置信阈值
- 是否允许自动扩展
- 审核状态
- 创建者
- 示例素材

参考模板：

```json

  "keyword": "露营氛围灯",
```

# 25. 为什么系统正式词库和用户词库必须分开

如果不分开，会有这些问题：

1. 用户乱加词会污染主库
2. 同义词关系会越来越乱
3. 难以回滚
4. 不同用户习惯会互相冲突
5. 工程上无法做权限和审核控制

所以建议：

- 系统词库：稳定、正式、可版本管理
- 用户词库：个性化、可编辑、可删除、可灰度启用
- 学习候选池：待审核、待升级，不直接参与主库污染

---

# 26. 自动学习与扩展机制

你希望 AI 能“自我学习并借此拓展语义”，这个可以做，但一定要有边界。

建议流程如下：

1. 从视频帧、图片、OCR、字幕、ASR、现有标签中抽取候选词
2. 做归一化处理：繁简、全半角、数字格式、大小写、停用词清理
3. 优先映射到已有标准词、别名、同义词
4. 对未命中的高频词做聚类
5. 分析这些词和现有标签的共现关系
6. 计算支持度、复现率、精确率、用户确认率
7. 达到阈值后进入 learning_candidate 候选池
8. 默认不直接写入系统主库
9. 用户或运营审核后，升级成：
   - 正式别名
   - 正式标签
   - 复合规则触发词
10. 长期低置信或易混淆的词定期清洗

---

# 27. 自动学习为什么不能“直接自动入库”

因为 AI 发现的新词很可能有这些问题：

- 歧义
- 短暂流行语
- OCR 误识别垃圾词
- ASR 错听
- 品牌型号碎片化
- 用户某个临时项目名

如果自动直接写入主库，时间久了词库一定会变脏。

正确方式是：

**先候选，后审核，再升级。**

---

# 28. 学习候选池应该记录什么

建议 learning_candidate 至少记录：

- 候选词文本
- 归一化文本
- 来源类型（OCR/ASR/视觉/用户反馈）
- 首次出现时间
- 最近出现时间
- 出现次数
- 涉及素材数
- 高共现标签
- 建议父分类
- 建议映射标签
- 用户确认次数
- 用户否定次数
- 当前状态（pending / approved / rejected）

# 29. 用户反馈闭环

用户反馈是这套系统持续变好的关键。

建议支持以下反馈动作：

1. 这个标签是对的
2. 这个标签是错的
3. 这个标签应该换成另一个
4. 新增一个别名
5. 新增一个自定义词
6. 屏蔽某个标签
7. 调高/调低某个标签阈值

这些反馈可以反过来用于：

- 调整标签阈值
- 调整共现加分
- 增加负向排除词
- 升级候选词
- 生成个性化标签偏好

# 31. 检索能力应该怎么理解

这套系统不仅是为了识别，更是为了后续检索和管理。

例如用户以后可能会搜：

- 海边日落的航拍视频
- 下雨天城市夜景
- 厨房做饭的生活感素材
- 带儿童和积木的亲子画面

- 精确检索
- 多条件筛选
- 语义召回
- 时间范围筛选
- 视频 segment 级命中定位

# 33. 实施顺序建议

最推荐的接入顺序是：

1. 导入大词库到 `tag / tag_alias / tag_relation`
2. 接入图片识别结果，先跑通 `asset -> evidence -> asset_tag_result`
3. 再接视频 `asset_segment`
4. 优先写 20 ~ 50 条高价值复合规则
5. 再做用户自定义关键词
6. 再做学习候选池
7. 最后再做用户反馈反哺

这是最稳妥的方式，因为它有几个优点：

- 不会因为用户乱加词把主库污染
- 每个标签为什么出现，都能解释
- 图片与视频能共用同一套结构
- 将来替换模型时，不用推翻整体设计

# 36. 这套系统最关键的产品原则

可以把下面这几句话当成整个设计的核心原则：

1. **不是堆更多词，而是把词组织对。**
2. **不是只识别一个标签，而是同时识别多个维度。**
3. **不是模型说什么就信什么，而是多证据融合后再决策。**
4. **不是让 AI 直接改主库，而是先候选、后审核、再升级。**
5. **不是把用户自定义词塞进系统词库，而是隔离管理、逐步吸收。**
6. **不是把视频当一堆独立帧，而是按时间段理解。**
7. **不是只为了识别，而是为了后续检索、管理、统计和复用。**
