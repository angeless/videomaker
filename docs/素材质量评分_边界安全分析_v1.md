# 素材质量评分体系 — 边界安全分析报告

**分析对象：** `素材质量评分_实现规格_v2_appendix.md`
**分析日期：** 2026-03-19
**分析目的：** 评估该实现方案是否会伤害原项目无关代码、弱化已有功能、边界控制是否充分
**结论：** 整体安全，有 1 个需要明确处理的风险点，其余均为纯增量改动

---

## 一、总结论

**该方案对现有系统的侵入性很低。** 核心设计思路是"新建独立模块 + 数据库纯新增列 + try/except 容错包裹"，不会删除、重命名、修改任何现有字段或逻辑。但有一个潜在的语义歧义需要明确处理（见下文第三节 RISK-001）。

---

## 二、逐项改动点安全审查

### 改动点 1：新增文件 `usability_scorer.py`

| 审查项 | 结论 |
|--------|------|
| 是否修改现有文件 | **否** — 纯新增文件 |
| 是否依赖现有模块内部实现 | **否** — 只读取已有函数的返回值（dict），不 import 任何现有类的内部方法 |
| 是否改变现有接口 | **否** — 不修改任何现有函数的签名、返回值、行为 |
| 如果此模块出错 | 被 try/except 包裹，不影响入库流程 |
| 回退方案 | 删除此文件 + 移除调用点即可，零残留 |

**结论：✅ 安全，无侵入**

---

### 改动点 2：数据库 ALTER TABLE — 4 个新列

```sql
ALTER TABLE assets ADD COLUMN usability_score REAL DEFAULT NULL;
ALTER TABLE assets ADD COLUMN usability_tier TEXT DEFAULT NULL;
ALTER TABLE assets ADD COLUMN material_type TEXT DEFAULT NULL;
ALTER TABLE assets ADD COLUMN trash_level TEXT DEFAULT 'none';
```

| 审查项 | 结论 |
|--------|------|
| 是否修改已有列 | **否** — 纯 ADD COLUMN，不改已有列的名称、类型、默认值 |
| 是否影响已有查询 | **否** — SQLite 的 `SELECT *` 会多返回几列但值为 NULL，不影响结构化访问（代码中均使用具名列读取）；已有 `SELECT uid, sha256, ...` 等精确列名查询完全不受影响 |
| 是否影响已有 INSERT | **否** — 已有 INSERT 语句明确列出列名（L5831-5839），新列有 DEFAULT NULL/DEFAULT 'none'，不需要已有 INSERT 语句修改即可兼容 |
| 是否影响 ON CONFLICT DO UPDATE | **否** — 已有 ON CONFLICT 子句只更新它自己列出的列，新列不在列表中，保持 DEFAULT 值 |
| Migration 模式 | 沿用现有 `_ensure_assets_columns()` 的 try/except 模式，列已存在则跳过，幂等安全 |
| 回退方案 | SQLite 不支持 DROP COLUMN（3.35.0 之前），但可以不写入值即可，列存在但全 NULL 不影响任何功能 |

**结论：✅ 安全，纯增量**

### 改动点 3：3 个新索引

```sql
CREATE INDEX IF NOT EXISTS idx_assets_usability ON assets(usability_score);
CREATE INDEX IF NOT EXISTS idx_assets_trash ON assets(trash_level);
CREATE INDEX IF NOT EXISTS idx_assets_material_type ON assets(material_type);
```

| 审查项 | 结论 |
|--------|------|
| 是否影响已有索引 | **否** — IF NOT EXISTS，纯新增 |
| 是否影响写入性能 | **极微** — 每条 INSERT/UPDATE 多维护 3 个 B-tree 节点，对于视频入库（本身就是秒级操作）可忽略 |
| 回退方案 | `DROP INDEX IF EXISTS` 即可 |

**结论：✅ 安全**

### 改动点 4：`_analyze_video()` 末尾插入评分调用

规格中的改动方式：

```python
# 在 return 之前插入
try:
    usability_result = score_asset(...)
except Exception as e:
    logger.warning("usability scoring failed: %s", e)
    usability_result = None
```

| 审查项 | 结论 |
|--------|------|
| 是否修改已有 return 值的字段 | **需要注意** — 规格将 usability_result 写入 `analysis_bundle["quality_assessment"]`，这是在 analysis dict 中**新增**一个 key，不覆盖已有 key |
| 是否改变已有流程 | **否** — try/except 包裹，失败时 usability_result = None，后续代码正常执行 |
| 是否影响 `_analyze_video()` 的已有返回字段 | **否** — 不修改 duration/resolution/quality_score 等任何已有返回字段 |
| 性能影响 | 规格要求 <5ms per score_asset 调用，纯内存计算，不访问磁盘/网络 |
| 失败时是否阻断入库 | **否** — try/except 保证失败只 log warning |
| 回退方案 | 移除这段 try/except 即可恢复原样 |

**结论：✅ 安全，有容错保护**

---

### 改动点 5：`_ingest_video_file()` INSERT 语句增加 4 列

| 审查项 | 结论 |
|--------|------|
| 是否修改已有列的写入逻辑 | **否** — 只在 INSERT 列表中追加 4 个新列及其值 |
| 如果 usability_result 为 None | 写入 NULL，DB 列 DEFAULT 值生效，不影响任何已有逻辑 |
| 是否影响已有 UPDATE 分支 | **需开发注意** — `_ingest_video_file()` 有两条路径：(1) 新素材走 INSERT（L5829-5900），(2) 已有素材走 UPDATE（L5732-5768 / L5770-5789）。规格中**只描述了 INSERT 路径**的改动，UPDATE 路径需要同步加入新列的更新，否则已有素材重新分析时不会更新 usability_score |

**结论：⚠️ 基本安全，但需补充 UPDATE 路径的改动说明（见 RISK-002）**

---

### 改动点 6：`search_videos.py` 排序增强

```python
# 原: results.sort(key=lambda x: x['match_score'], reverse=True)
# 改: results.sort(key=lambda x: (x["match_score"], x.get("usability_score", 0) or 0), reverse=True)
```

| 审查项 | 结论 |
|--------|------|
| 是否改变主排序逻辑 | **否** — match_score 仍是第一排序键，usability_score 只在 match_score 相同时作为 tiebreak |
| 如果 usability_score 为 None | `x.get("usability_score", 0) or 0` 保证 fallback 到 0，不会报错 |
| 是否影响无评分素材的排序 | **否** — 无评分素材 usability_score=0，tiebreak 不影响它们与有评分素材之间的相对顺序（因为主排序键 match_score 已经决定了） |
| 回退方案 | 恢复原排序 lambda 即可 |

**但请注意：** 实际看了 `search_videos.py` 源码后，当前的搜索是基于 JSON 索引文件的 `VideoSearch` 类（L14-80），不是直接查 DB 的。规格中写的 `x.get("usability_score")` 需要确认搜索结果 dict 中是否真的包含这个字段。**如果搜索走的是 JSON 索引而不是 DB 查询，则需要在索引构建时也写入 usability_score。** 这是一个需要开发确认的对接细节。

**结论：⚠️ 逻辑安全，但需确认搜索结果数据源是否包含 usability_score**

### 改动点 7：新增 `tools/backfill_usability_scores.py` 迁移脚本

| 审查项 | 结论 |
|--------|------|
| 是否修改已有代码 | **否** — 纯新增独立脚本 |
| 是否影响运行中系统 | **否** — 手动执行，不自动触发 |
| 操作安全性 | 只 UPDATE 新增列（usability_score/tier/material_type/trash_level），不碰已有列 |
| 回退方案 | `UPDATE assets SET usability_score=NULL, usability_tier=NULL, material_type=NULL, trash_level='none'` |

**结论：✅ 安全**

## 三、已识别风险点

### RISK-001（中）：`quality_score` 字段的语义歧义

**现状：** assets 表已有一个 `quality_score` 列（L367），当前存储的是 `technical_analysis()` 返回的 `overall_quality`，即 `(resolution_score + bitrate_score) / 2` 的技术质量分。

**风险：** 实现规格新增了 `usability_score` 列，两者是不同维度的评分。但如果开发者误以为新的 usability_score 应该替换旧的 quality_score，就会导致：
- 已有依赖 quality_score 的逻辑（如 `_infer_quality_tier()` L4052-4061、`_build_semantic_bundle()` 中引用 quality_score 的地方）行为改变
- 已入库素材的 quality_score 含义前后不一致

**实际规格设计：** 规格中 quality_score 保持不变，新增独立的 usability_score 列。**规格本身没有要求替换 quality_score。**

**建议：** 在实现规格文档中显式加一条声明："`quality_score` 列保持原有含义（resolution+bitrate 技术分），不做任何修改。新增的 `usability_score` 是独立的七维综合评分，两者并存。"

---

### RISK-002（低）：UPDATE 路径遗漏

**现状：** `_ingest_video_file()` 中，已有素材重新分析时走的是 UPDATE 语句（L5732-5768），但规格只描述了 INSERT 路径（L5829-5900）的新列写入。

**风险：** 已有素材触发重新分析（semantic_version 升级等）时，即使重新计算了 usability_score，也不会写入 DB。

**建议：** 补充 UPDATE 路径中也要 SET usability_score=?, usability_tier=?, material_type=?, trash_level=?

**影响范围：** 仅影响"已入库素材重新分析"的场景，新入库素材不受影响。不会造成数据损坏，最坏情况是某些老素材的 usability_score 保持 NULL。

---

### RISK-003（低）：search_videos.py 数据源对接

如上文改动点 6 所述，当前 `search_videos.py` 是基于 JSON 索引文件搜索的，不直接查 DB。如果搜索结果 dict 中没有 `usability_score` 字段，排序增强实际上不会生效（但也不会报错，因为有 `get(..., 0)` 兜底）。

**建议：** 确认搜索是否还走 JSON 索引，如果是，需要在索引构建环节也写入 usability_score。或者如果项目已经切换到 DB 直查搜索，则此风险不存在。

---

### RISK-004（极低）：`_get_library_stats()` 性能

新增的 `_get_library_stats()` 方法会在每次 `_analyze_video()` 时执行一次 `SELECT COUNT(*)` 和一次 `GROUP BY` 查询。

**影响：** 当素材库规模达到万级以上时，GROUP BY 查询可能需要几十毫秒。但由于 `_analyze_video()` 本身就是秒级操作（含视觉分析、音频分析等），这个开销可忽略。

**兜底：** 规格中 `library_stats` 参数是 Optional，即使不传也有默认值，不会阻断评分。

## 五、边界控制总评

| 边界维度 | 评估 |
|---------|------|
| 代码隔离 | ✅ 新逻辑集中在独立的 `usability_scorer.py`，不侵入已有模块内部实现 |
| 数据隔离 | ✅ 新增列 DEFAULT NULL/DEFAULT 'none'，不覆盖已有数据 |
| 失败隔离 | ✅ try/except 包裹，评分模块崩溃不影响入库流程 |
| 依赖方向 | ✅ 单向依赖：`usability_scorer.py` 读取已有数据，已有模块不依赖新模块 |
| 回退成本 | ✅ 移除 import + try/except 代码块 + 新文件即可完全回退 |
| 版本兼容 | ✅ USABILITY_SCHEMA_VERSION 独立于 SEMANTIC_SCHEMA_VERSION |

## 六、给开发的建议

1. **显式声明 quality_score 不变** — 在代码注释和 PR 描述中明确标注
2. **补充 UPDATE 路径** — 在 `_ingest_video_file()` 的两个 UPDATE 语句中也加入 4 个新列的写入
3. **确认搜索数据源** — 确认 search_videos.py 的排序增强是否需要同步到 JSON 索引构建流程
4. **先合入 DB migration** — 建议先单独合入 `_ensure_assets_columns` 的改动，确认线上 DB 兼容后再合入评分逻辑
5. **灰度验证** — 先用 backfill 脚本对 10-20 条素材跑评分，人工确认结果合理后再全量

---

## 七、最终结论

> **该实现方案整体安全，不会伤害原项目的无关部分，不会弱化已有功能。** 所有改动均为纯增量（新增文件、新增列、新增索引），核心入库流程有 try/except 容错保护。唯一需要开发额外注意的是 RISK-001（quality_score 语义歧义的显式声明）和 RISK-002（UPDATE 路径补全），这两个都是低成本、低风险的补充工作。
